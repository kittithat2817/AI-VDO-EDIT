# CapCut Story Planner

จัดเรื่องจากสื่อในโปรเจกต์ที่ผู้ใช้ระบุ แล้วส่งให้ `capcut-script-edit` ทำต่ออัตโนมัติเมื่อไฟล์ ช่วงเวลา และความหมายหลักชัดเจน ผลลัพธ์คือแผนที่ตรวจย้อนกลับได้ ไม่ใช่การเขียนบทพูดใหม่ ทั้งการสำรวจและการตัดต่อทำผ่านไฟล์บนดิสก์เท่านั้น ไม่เปิด ปิด หรือควบคุม CapCut รวมถึง UI automation, keyboard/mouse, deep link, app launch หรือคำสั่งแอปเบื้องหลัง

## 1. สำรวจโปรเจกต์

ใช้โปรเจกต์ที่ระบุในคำขอหรือที่ตรวจยืนยันได้จากงานปัจจุบัน ถ้ามีหลายโปรเจกต์และระบุเป้าหมายไม่ได้ ให้ถามเลือกโปรเจกต์ สำรวจทั้ง Media ที่นำเข้าและ Timeline ที่ใช้งานอยู่ รวม compound/subproject ที่อ้างถึง แยกคลิปพูด ภาพประกอบ และเสียงประกอบตามเนื้อหาจริง ชื่อไฟล์ใช้ระบุตัวตนเท่านั้น

อ่านไฟล์โปรเจกต์และ media registry ที่เข้าถึงได้แบบอ่านอย่างเดียว ตรวจ active timeline และบัญชีสื่อจากข้อมูลบนดิสก์จริง รูปแบบ draft อาจต่างตามรุ่น หากไฟล์อ่านไม่ได้หรือถูกเข้ารหัส ให้ทำแผนส่วนที่มีข้อมูลและหยุดเฉพาะขั้นเขียน หากไฟล์สื่อหาไม่พบให้บันทึกข้อจำกัดแทนการเดา ห้ามถือว่ามีเพียง root draft หรือเลือก UUID แรกโดยไม่มีหลักฐาน และไม่ใช้การควบคุมแอปเป็นทางแก้

เก็บ `inventory.json` ตาม [สัญญาแผน](references/plan-contract.md): project/timeline identity, สื่อทั้งสองแหล่ง, material IDs, path จริง, ประเภทสื่อ และ duration จากไฟล์จริง คลิปบน Timeline เก็บทั้ง source range และตำแหน่งเดิมแยกกัน รวมสื่อซ้ำที่อ้างไฟล์เดียวกันโดยรักษา material IDs เดิมไว้

**จบขั้นเมื่อ:** บัญชีสื่อครอบคลุมทั้ง Media และ active Timeline หรือระบุส่วนที่สำรวจไม่ได้ไว้อย่างชัดเจน ใช้สื่อของโปรเจกต์และ preset ที่ผู้ใช้อนุญาตไว้ใน SOP พร้อมเก็บ provenance; ไฟล์อ้างอิง/SOP ไม่ถูกนำเข้าเป็นฟุตเทจโดยปริยาย

## 2. เข้าใจเนื้อหาและเลือกโครง

ถอดเสียงในเครื่องเป็นค่าเริ่มต้น ใช้ ASR ที่มีพร้อม timestamp ระดับคำหรือช่วงสั้น ทดสอบความอ่านรู้เรื่องกับคลิปตัวอย่างก่อนประมวลผลต่อ ตรวจเทียบภาพ/ซับ/เสียงต้นฉบับในช่วงสำคัญ โดยเฉพาะชื่อสินค้า คำปฏิเสธ เงื่อนไข ตัวเลข และรอยตัด ASR เป็นหลักฐานอัตโนมัติ ไม่ใช่คำพูดที่รับรองแล้ว การอัปโหลดสื่อเพื่อใช้โมเดลภายนอกต้องมีการอนุญาตสำหรับงานนั้น

เก็บ transcript ดิบและบันทึกการแก้พร้อมหลักฐาน หากถอดผิดมากให้ลองเครื่องมือหรือโมเดลในเครื่องที่เหมาะสมและเปิดเผยการเปลี่ยน หากยังไม่ชัด ให้เว้นช่วงนั้นและทำส่วนอื่นต่อ ถ้าความไม่ชัดเปลี่ยนความหมายหลักของเรื่อง ให้ถามเฉพาะประเด็นนั้น

อ่าน SOP ที่ผู้ใช้ให้เป็นหลัก ทุกคอนเทนต์แนวทดลองหรือขายสินค้าของผู้ใช้ใน workflow นี้ อ่าน [SOP preset เครื่องหมาย-อย.](references/product-mark-preset.md) และคง `product_mark` ในแผน ใช้ profile `user-product-content` สำหรับงานทั่วไปในขอบเขตนี้ สำหรับคลิปแฮมแฮงค์ที่ใช้ SOP เดิม อ่าน [โปรไฟล์ SOP](references/hamhang-sop.md) และใช้ `hamhang-experiment` ใน [โปรไฟล์เครื่องอ่าน](references/profiles.json) ซึ่งคงข้อบังคับเฉพาะสินค้าครบ สำหรับคลิปสอนหรือประสบการณ์ ใช้เฉพาะข้อ SOP ที่เกี่ยวข้อง

งานโปรโมชันหรือปิดการขาย BOFU อ่าน [แนวทาง BOFU](references/promotion-bofu.md) เลือกเข้าโปรไวหรือเก็บมุกและเหตุผลซื้อตามบรีฟและวัตถุดิบ ยืนยันข้อเสนอ วันโปร เงื่อนไข และ CTA ก่อนเลือกช่วงขาย ส่งข้อมูลที่ยืนยันพร้อมแผน และเลือก SOP ตามสินค้าปัจจุบัน

ใช้คลิปอ้างอิงเป็นตัวอย่างหน้าที่ของแต่ละช่วงและจังหวะการเปลี่ยนสาร แยกออกจากไฟล์/เวลา/ข้อกล่าวอ้างของงานใหม่ อ่าน [ขอบเขตคลิปอ้างอิง](references/reference-pattern.md) เมื่อใช้งานตัวอย่างเหล้าทำลายตับ

**จบขั้นเมื่อ:** ระบุได้ว่าคลิปต้องการให้คนดูเข้าใจอะไร เป้าหมายตอนจบคืออะไร และมีช่วงต้นฉบับใดรองรับแต่ละประเด็น

เมื่อพบการเริ่มสารเดิมใหม่ ให้เทียบทั้งประเด็นและประโยคถัดไป รวมการพูดต่างถ้อยคำหรือข้ามคัต เลือกเทคที่ผู้ใช้ยืนยันหรือเทคที่ครบความและต่อเรื่องได้ก่อนใช้ลำดับท้ายเป็นตัวตัดสิน อ่านขั้นเลือกเทคใน [editorial-contract](references/editorial-contract.md) สำหรับ QC การพูดซ้ำให้เปิด `require_content_review` และทบทวนทุก beat กับรอยต่อ ไม่ใช้ผลตรวจ mapping แทนการตัดสินความสมบูรณ์ของคำพูด

ก่อนเลือกเทคซ้ำหรือช่วงมีคำสั่งทีมงาน อ่าน [ข้อจำกัดการเลือกเนื้อหาและซับ](references/editorial-contract.md) แยกบทบาทผู้พูดพร้อมหลักฐานและความไม่แน่ใจ ใช้ช่วงห้ามเลือกและตอนจบที่ต้องรักษาจากบรีฟ ไม่ใช้ ASR ที่พูดครบประโยคเป็นหลักฐานว่าเป็นผู้ทำคอนเทนต์

## 3. เรียงเรื่องจากประโยคหรือประเด็นที่จบความ

เลือก take ที่ความหมายครบ ชัด และภาพสัมพันธ์กับคำพูด แบ่งไฟล์เดียวเป็นหลายช่วงและย้ายข้ามไฟล์ได้ ตัดความซ้ำ/ออกนอกเรื่องก่อนย่อเหตุผลที่จำเป็น เก็บคำปฏิเสธ ข้อยกเว้น เงื่อนไข และคำชี้ว่าเป็นการจำลองไว้กับข้อความที่เกี่ยวข้อง

ตรวจรอยต่อด้วยการอ่านลำดับที่เลือกเป็นเรื่องเดียว: คำว่า “สิ่งนี้/แบบนี้/เพราะฉะนั้น/อีกครั้ง” ต้องมีสิ่งอ้างถึงก่อนหน้า คำถามต้องมีคำตอบ และภาพก่อน–หลังต้องไม่ทำให้ผลทดลองเปลี่ยนความหมาย จบที่คำตอบ/ข้อสรุปหรือ CTA ที่วัตถุดิบและโจทย์รองรับ

กำหนดความยาวจากเนื้อหาจำเป็นและข้อจำกัดของแต่ละงาน ไม่ใช้ 60 วินาทีเป็นเพดานโดยปริยาย ไม่บังคับใช้ทุกไฟล์หรือทุกช่วงของโครง ส่วนเสริมที่ไม่มีข้ามได้ เก็บข้อบังคับ SOP ที่ยังขาดเป็นรายการส่งต่อพร้อมแนวทางใช้ข้อความจาก SOP หรือสื่อที่มีอยู่ โดยไม่สร้างคำพูด/เสียงพูด/คำกล่าวอ้างใหม่เพื่อเติมช่องว่าง

หากบรีฟกำหนดเสียงปิด ให้จอง source span ที่พูดครบเป็น protected ending ก่อนย่อเรื่อง และส่ง caption profile ที่ผู้ใช้เลือกให้ editor แยกจาก transcript เต็ม เมื่อเป็น selective captions ให้ออกแบบสารที่ขึ้นจอ ไม่สร้างซับตามทุกคำแล้วค่อยย่อ

สร้าง `story-plan.json` และ `story-plan.md` ตาม [สัญญาแผน](references/plan-contract.md) ทุก beat มี source file/range, หน้าที่, เหตุผลที่วางตรงนี้ และเหตุผลที่เชื่อมกับช่วงถัดไป แยกความไม่แน่ใจเฉพาะจุดออกจากปัญหาที่เปลี่ยนความหมายหลัก

**จบขั้นเมื่อ:** เรื่องอ่านต่อกันเข้าใจได้ ทุกช่วงอ้างต้นฉบับได้ และส่วนที่ข้าม/ยังขาดมีเหตุผลบันทึกไว้

## 4. ตรวจแผนและส่งให้สกิลตัดต่อ

รันตัวตรวจด้วย path ของสกิลที่โหลดอยู่:

```bash
python3 <skill-directory>/scripts/validate_plan.py <job-directory>/inventory.json <job-directory>/story-plan.json --check-media
```

ตัวตรวจเช็กขอบเขตโปรเจกต์ การอ้างไฟล์ ช่วงเวลา การต่อ Timeline และรายการ SOP แต่ไม่รับรองความถูกต้องทางความหมาย ต้องทำการตรวจรอยต่อในขั้น 3 ด้วย ผล `handoff_ready` แยกจาก `sop_complete`: รายการบังคับที่ยังขาดส่งให้สกิลตัดต่อจัดการต่อได้ และต้องปรากฏในรายงานจนกว่าจะเติมครบ

เมื่อแผนพร้อม อ่านสกิล `capcut-script-edit` ที่ติดตั้งอยู่จริงและ [วิธีส่งต่อ](references/editor-handoff.md) แล้วดำเนินงานต่อในคำขอเดียวกัน เก็บ plan/inventory/transcripts และ source→edited mapping ไว้ก่อนแก้ไข หากผู้ใช้ขอวิเคราะห์หรือแผนอย่างเดียว ให้ตั้ง handoff.mode เป็น plan_only และจบตามขอบเขตนั้น

แจ้งสถานะตามหลักฐาน: แผนพร้อม, เขียน native draft แล้ว, หรือตรวจไฟล์และสื่อแล้ว เป็นคนละสถานะ ส่ง draft ที่แก้ไขต่อได้พร้อมผลตรวจบนดิสก์ การมี JSON ไม่ใช่หลักฐานว่าแอปเปิด เล่น หรือ render ได้ การพรีวิวภายนอกทำเฉพาะเมื่อผู้ใช้ขอและระบุว่าเป็น external preview หากรูปแบบไฟล์ยังไม่รองรับ ให้ส่งแผนที่เสร็จแล้วพร้อมข้อจำกัดของขั้นเขียน
